# v0.1.0-beta.12

Fluentic now publishes generated TypeScript declarations for its public APIs.
Consumers use compiled JavaScript at runtime and `.d.ts` files for type checking,
so their compiler settings no longer cause Fluentic implementation files to be
checked as application source.

## Changes

- Generate declarations for every public type export, including JSX runtimes,
  framework augmentations, adapters, compiler APIs, and bundler integrations.
- Build declarations during packaging and use explicit relative module extensions
  for Node16/NodeNext compatibility.
- Make `@babel/core` and its declaration dependency explicit package dependencies;
  compiler/Vite users no longer need to install Babel separately for Fluentic.
- Correct Solid JSX augmentation so framework exports remain available under full
  declaration checking, including HTML and SVG `css` attributes. Declare Solid as
  an optional framework peer.
- Resolve runtime exports when statically evaluating imported values. This keeps
  Tailwind theme extraction working when type exports point to declarations.
- Add isolated tarball consumer checks and a documented release workflow. Disable
  Changesets' package-prefixed Git tags and private example version bumps.

## Upgrading

After this version is published to npm:

```sh
pnpm add @fluentic/style@0.1.0-beta.12
```

Remove version-specific patches that redirected Fluentic's type exports to local
`.d.ts` files, then reinstall and run your application's checks. Keep your strict
TypeScript settings enabled. Public runtime APIs are unchanged.

This packaging change does not prove that Fluentic's implementation passes
`noUncheckedIndexedAccess`; it separates library implementation checking from
consumer API checking.

## Validation

`pnpm release:check` passed: lint/format checks, all 24 workspace TypeScript
projects, 361 library tests, configured example and benchmark builds, Next.js
production verification, and isolated packed consumers. Next.js verification checked
extracted CSS and rendered routes `/`, `/ssg`, `/ssr`, `/rsc`, and `/client`. Packed consumer checks use `strict`, `noUncheckedIndexedAccess`, and
`skipLibCheck: false`; the export/JSX matrix also enables `exactOptionalPropertyTypes`.

The ESM consumer matrix covers Bundler, Node16, and NodeNext resolution. Next.js
integration declarations are checked in Bundler mode, matching the Next.js example;
Next.js 16.2.9's own declarations do not pass the Node16/NodeNext matrix.

React, Preact, Solid, and Tailwind examples are type-checked and built against the
packed package. The tests verify export targets exist, reject invalid API use,
and assert that no Fluentic implementation source enters the consumer program.

The development watcher was also verified to regenerate declarations after a public
type change and after restoring the source.
